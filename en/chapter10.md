# Chapter 10: What AI Changes and What It Doesn't

The structure of this booklet was made before AI could do all the programming the way it does now. So you may wonder whether all this still holds in an age when AI does the programming for you.

To give the conclusion first: it all still holds. Nothing discussed so far changes in principle because of AI. Some processes may become more efficient. For example, you'll be able to build high-fi prototypes very quickly. If the basic frame of the product has already been validated, as when slightly changing an existing product, you might even skip low-fi prototyping. But you should stay true to the purposes of prototyping described earlier. One of the most common misconceptions is that since high-fi prototypes can be built in no time, it's better to run every usability test with a high-fi prototype. I disagree. As discussed in [Chapter 5](chapter5.md), when a prototype looks finished, users tend not to give feedback on what really matters and instead give feedback on overly detailed things. Then you don't get the feedback you need from usability testing, and you waste time. It's important to make clear what users should focus on in their feedback. And that matters regardless of AI.

Building a product broadly splits into two parts: deciding what to build, and actually building it. There's no clean boundary between them, but that's roughly it. This booklet is about the process of deciding what product to build. What AI currently takes care of is mainly the latter, the building. Figuring out what to build so that users are satisfied is still, for now, largely up to people. There seem to be many attempts to replace this with AI as well. But it is much harder than getting AI to write code. You can check right away whether code works, but you can't check whether users are satisfied until you actually meet them.

If anyone thinks that AI can automate all of software development, I hope reading this booklet changes their mind a little.
