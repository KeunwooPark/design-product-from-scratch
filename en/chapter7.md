# Chapter 7: Communicating Design

Strictly speaking, the design so far is design at a conceptual level. Countless things still have to be decided before it can actually be built. If your company has a design system, you first need to redefine the product you've designed so far to fit that design system. If the design system needs changes in the process, you need to make them too. If there is no design system, it's good to settle a minimal set of rules at this stage, covering colors, fonts, spacing, and frequently used components. These rules become the seed of a future design system.

Communication between developers and designers through a design system is a huge topic on its own. Interestingly, even when the developer and the designer are the same person, it's hard to close the gap between design and development. And there is no single good way to solve this problem. Tools such as Figma don't fully solve it either. Ideally, you'd create a file in which the design and the implementation are **defined together** at a reasonably concrete level. Everyone can then look at the same thing to make decisions, and that makes communication more efficient than talking while looking at different things. Put simply, it means creating a [single source of truth (SSOT)](https://en.wikipedia.org/wiki/Single_source_of_truth). But there is no magic tool that solves this problem. You need to build a process for creating and maintaining such an SSOT file using the various tools your company uses.

What matters is not to forget that even if you've designed something close to the real product in a prototyping tool such as Figma, a great many steps remain before it's implemented. Otherwise, a lot of conflict can arise on the way to the actual implementation. This is an important issue even if you design and develop on your own. If you start coding straight from the design file, you'll find midway that you have to change the structure of the system. Designing the structure of the system before you start developing applies to interfaces too. Because the interface is visible, it's easy to mistake it for already being designed, but a design file only describes the visible structure, not the structure of the software system. Another important point is that designers and developers should do this process together. While designing the interface's system for implementation, the design may need to change. And since the SSOT file mentioned above has to be updated, discussing it together is essential.

Wrapping up this process and passing what follows to the development team is commonly called a [handoff](https://www.interaction-design.org/literature/topics/design-handoffs). If the design team includes both developers and designers, the handoff is very natural. If marketers were on the design team too, the marketing team also ends up with a deep understanding of the final product. That's why product design is best done by a varied group of people.
